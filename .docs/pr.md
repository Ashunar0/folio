## 📌 1. 課題（なぜこれを作ったか）
背景課題：大学サークルの会計管理の現実

大学サークルなどの小規模組織では、会計業務が LINE・Google フォーム・スプレッドシートの寄せ集め運用 で回っており、以下の問題が発生していました：


問題点 | 具体例
--- | ---
データの散在 | LINEで経費申請 → スプレッドシートに手動転記 → 漏れや重複が発生
承認フローの不在 | 誰が承認したか、いつ承認されたかが不明瞭
引き継ぎの困難 | 毎年会計担当が変わるたびに運用方法がリセット
権限管理の欠如 | 全員が全データを編集できてしまう危険性
レシート管理の煩雑さ | 紙レシートの紛失、写真がLINEに散らばる


解決する価値：
**「申請〜承認〜台帳管理」までの全プロセスを統合し、誰でも簡単に使える軽量会計SaaS を提供する**

## 💡 2. 工夫した点

### ① マルチテナント × RBAC 設計（技術的工夫）
複数チーム所属対応：1ユーザーが複数サークルに所属できる設計（Slack/Notionモデル）
4段階のロール設計：admin / manager / member / viewer で権限を細かく制御
RLS（Row Level Security） で DBレベルでの完全なデータ分離を実現
チーム外のデータは絶対に参照できない
承認済みデータは編集不可を DB で保証

```sql
-- 例：チームスコープを強制するRLSポリシー
team_id IN (
  SELECT team_id FROM team_users WHERE user_id = auth.uid()
)
```

### ② 承認ワークフローの設計
経費は draft → submitted → approved/rejected と状態遷移
承認されたデータは transactions テーブルに複製 → 台帳の整合性を確保
approved データは編集不可（会計システムとしての信頼性）

### ③ 招待フローの UX 設計
複数経路からチーム参加可能：招待リンク、オンボーディング画面、チームスイッチャー
フルリンク or トークンの柔軟な入力 に対応（ユーザビリティ向上）
ログイン後のスマートリダイレクト（所属チーム数に応じた適切な画面へ）

### ④ 運用コストゼロを目指した技術選定
技術 | 理由
--- | ---
Next.js + Supabase | バックエンド不要のBaaS直結構成
Vercel | GitHub push で自動デプロイ
Supabase Free Tier | Auth/DB/Storage が月額 ¥0
→ 年間 2000円以内で運用可能な SaaS を実現

### ⑤ チーム作成時のデフォルトカテゴリ自動生成
新規チーム作成時に、よく使うカテゴリ（交通費、飲食費など）を自動挿入
即使い始められる体験を提供

## 😰 3. 苦労した点

### ① RLS ポリシーの罠
問題：招待リンクの受信者がチーム情報を読めない
原因：teams テーブルの RLS が team_users 所属を前提
解決：「招待経由でのチーム情報閲覧」を許可するポリシーを追加
CORSエラーに見える → 実は RLS 違反だった（Supabase はエラー時に CORS ヘッダーを返さない）

### ② Next.js 15 の破壊的変更
params が Promise になり、await が必要に
useSearchParams() が Suspense 境界なしだと SSR エラー
公式ドキュメントを追いながら対応

### ③ Hydration Mismatch（SSR/CSR の不整合）
Radix UI の Tabs で ID がサーバー/クライアントで不一致
解決策：マウントガードを導入し、クライアントサイドのみでレンダリング

```tsx
const [mounted, setMounted] = useState(false);
useEffect(() => setMounted(true), []);
if (!mounted) return <Skeleton />;
```

### ④ React Query キャッシュの落とし穴
チーム参加後に TeamProvider が更新されない
router.push() → window.location.href に変更してフルリロード
localStorage でチーム選択を永続化する仕組みを追加

### ⑤ 権限制御の二重チェック
- UI 側：ボタンの表示/非表示を制御
- DB 側：RLS で操作自体をブロック
両方やらないとセキュリティホールになる → 実装漏れを何度か経験
