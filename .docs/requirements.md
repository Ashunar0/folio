# **Folio 要件定義書（完全版）**

## 1. アプリ概要

- **目的（Why）**
  大学サークルなどの小規模組織の会計業務（経費申請・承認・管理）が、
  LINE・Google フォーム・スプレッドシートなどの寄せ集め運用で破綻しがちな問題を解決する。
  **申請〜承認〜台帳管理までの全プロセスを統合し、誰でも簡単に使える軽量会計 SaaS を提供する。**

- **ターゲット（Who）**

  - 大学サークルの代表 / 会計担当者
  - 学園祭実行委員会・学生団体
  - 小規模グループ（5〜50 名）

- **利用シーン（When/Where）**

  - サークルメンバーが経費を申請するとき
  - 会計担当が承認作業を行うとき
  - 会計管理の引き継ぎ時
  - イベント単位で収支を把握したいとき
    PC・スマホの両方で利用される。

- **価値提供（What）**

  - 経費申請〜承認〜記帳までを **1 つのアプリで完結**
  - カテゴリ・イベント単位で管理できる
  - 安心の権限管理と安全な承認フロー
  - 年次で会計担当が変わっても“崩れない”仕組み
  - シンプルで直感的な UI（shadcn / Linear-like UI）

- **規模**
  個人開発想定。
  最大チーム数 100、ユーザー数〜1,000 程度を想定。

- **技術スタック（How）**

  - **フロントエンド**: Next.js (App Router), TypeScript, shadcn/ui
  - **バックエンド / DB**: Supabase（Auth / Database / RLS / Storage）
  - **ホスティング**: Vercel
  - **その他**: Supabase Edge Functions（必要なら）

## 2. 機能要件

### 🎯 MVP 機能（優先度つき）

| 優先度 | 機能名                                | 概要                                                 | ユーザーストーリー                   |
| :----: | :------------------------------------ | :--------------------------------------------------- | :----------------------------------- |
|  ★★★   | **経費申請（Expense Form）**          | 日付・金額・カテゴリ・イベント・メモ・レシートを登録 | メンバーが経費を申請できる           |
|  ★★★   | **承認ワークフロー（Approval）**      | Manager/Admin が申請を承認 or 差戻し                 | 会計担当が申請内容を確認し承認できる |
|  ★★★   | **Transactions（台帳）**              | 承認済の支出を一覧で管理                             | 会計担当が支出状況を確認できる       |
|  ★★★   | **チーム管理（Team Settings）**       | 権限設定、招待、カテゴリ管理、イベント管理           | Admin/Manager がチームを運用できる   |
|  ★★☆   | **メンバー一覧（Users）**             | 全メンバーの表示、権限変更（Admin のみ）             | 誰が所属しているか把握できる         |
|  ★★☆   | **マルチチーム対応（Team Switcher）** | ユーザーが複数チームに所属し切り替えできる           | 複数団体で使える                     |
|  ★☆☆   | **個人設定（My Settings）**           | 名前、テーマカラー、プロフィール編集                 | ユーザーの体験をカスタムできる       |

## 3. 非機能要件

| 分類           | 要件                                                            |
| :------------- | :-------------------------------------------------------------- |
| パフォーマンス | 主要操作は 2 秒以内で表示。テーブルはページネーション推奨。     |
| セキュリティ   | Supabase Auth / RLS による権限制御。HTTPS 強制。XSS/CSRF 対策。 |
| 認証           | Email + パスワード、招待リンク経由でのチーム登録に対応。        |
| ストレージ     | レシートは Supabase Storage に保存。アクセス制御は RLS で保護。 |
| 信頼性         | エラー時は UI に明示し、再試行可能にする。                      |
| 可用性         | Vercel 自動デプロイ、GitHub 連携。                              |
| 拡張性         | テーブル定義を疎結合にして後の機能追加に耐える。                |

## 4. 追加仕様（← ここが今回あなたが補足してくれた重要ポイント）

### ● カテゴリ・イベント管理

- 共通のプリセット（交通費・宿泊費など）を提供
- 各チームは独自カテゴリを追加可能
- プリセットカテゴリは編集不可、安全性を確保

### ● Danger Zone

- Admin のみアクセス可能
- チーム削除
- 招待リンク無効化
- チーム所有権の譲渡
- カテゴリ / イベントの初期化（optional）

### ● レシートアップロード

- `<input type="file" accept="image/*">` によりスマホでカメラ／アルバム選択が可能
- Supabase Storage に保存し、RLS でチーム毎にアクセス制限

### ● 承認済データの編集方針

- **approved のデータは編集不可**
- 誤りへの対応は「Admin/Manager による削除 → 再申請」
- 会計システムとしての整合性を最優先

### ● ロール設計

ロールは 4 種（viewer / member / manager / admin）
ただしロールは **文字列で保持し将来的な追加に対応可能な設計**。

### ● Multi-team（複数チーム所属）

- User は複数 team に所属可能
- team_users 中間テーブルで管理
- サイドバー上部に team switcher を配置
- すべてのデータクエリは current_team_id に依存

## 6. 想定ユーザーフロー

### ● 招待リンクからチーム参加

1. Admin が招待リンクを発行
2. 新規ユーザーがリンクを踏む
3. Signup or Login
4. Supabase が user を作成
5. team_users に member 権限で追加
6. Dashboard に遷移

### ● 経費申請〜承認〜台帳反映

1. Member が Expense Form から申請
2. Approval ページに“申請中”が表示
3. Manager/Admin が承認
4. approved データが Transactions に反映
5. Member からの編集は不可
6. 間違いがあれば Manager/Admin が削除 → 再申請
